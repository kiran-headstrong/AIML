18. Trainer / Evaluator Q&A

🎓 AI Training Assistant for New Employees

An AI-powered onboarding assistant that answers employee questions using RAG (Retrieval-Augmented Generation) with semantic search and grounded LLM responses.

Project Goal: Build a chatbot that helps new employees at TechNova Solutions find answers about company policies, onboarding procedures, and general company information — grounded entirely in internal documents with source attribution.

1. Introduction

New employees often have many questions during their first weeks — about leave policies, expense claims, IT setup, and company culture. This AI Training Assistant provides instant, accurate answers by searching through company documents and generating context-aware responses.

Key Differentiator: Unlike a generic chatbot, this assistant only answers based on retrieved company documents. It cites sources, reports confidence scores, and gracefully handles questions it can't answer.

Problem Statement

How can we build an intelligent assistant that:

  • Answers employee questions accurately using internal documents
  • Classifies queries into meaningful categories
  • Provides source attribution for every answer
  • Runs for free using local embeddings and free-tier LLM inference
  • Installs easily without heavy dependencies (no PyTorch, no C++ compiler)

3. System Architecture

graph LR A[User Question] --> B[Query Router] A --> C[Embedding Model] B --> D[Category Classification] C --> E[Vector Store Search] E --> F[Top-5 Relevant Chunks] F --> G[LLM Generation] D --> G G --> H[Response + Sources + Confidence]

High-Level Flow

Pipeline Steps:
  1. User Query → User types a question in the Gradio chat UI
  2. Query Routing → LLM classifies the intent (company/policy/onboarding/general)
  3. Embedding → Question is embedded using all-MiniLM-L6-v2 (ONNX)
  4. Retrieval → Top-5 most similar document chunks found via cosine similarity
  5. Filtering → Chunks below 0.3 similarity threshold are discarded
  6. Generation → Retrieved context + question sent to Groq LLM
  7. Response → Clean answer with sources and confidence score returned

4. RAG Pipeline

What is RAG?

Retrieval-Augmented Generation combines two components: a retrieval system that finds relevant documents, and a language model that generates answers based on those documents. This grounds the LLM's responses in factual data rather than relying on memorized knowledge.

5. Embedding Engine (ONNX)

Why ONNX instead of PyTorch? The standard sentence-transformers library pulls in PyTorch (~2.5GB), which causes Windows path-length errors in deeply nested projects. ONNX Runtime is ~14MB and provides identical embeddings without any compilation or heavy dependencies.

Model: all-MiniLM-L6-v2

PropertyValue
Model Size~90MB (ONNX format)
Embedding Dimensions384
Max Sequence Length256 tokens
Inference BackendONNX Runtime (CPU)
Similarity MetricCosine similarity (L2 normalized)

Embedding Pipeline

# Simplified embedding flow
1. Tokenize text → input_ids + attention_mask
2. Run ONNX inference → token embeddings (batch × seq_len × 384)
3. Mean pooling → sentence embedding (batch × 384)
4. L2 normalize → unit vectors for cosine similarity

6. Vector Store (NumPy)

Analogy: Think of the vector store as a library index. Each document chunk is a book, its embedding is its location code, and a query is like asking "find me books similar to this topic." Cosine similarity measures how close two books are in the index.

Storage Format

FileFormatContents
embeddings.npyNumPy binaryMatrix of shape (N, 384) — all chunk embeddings
documents.jsonJSONChunk text + source metadata for each embedding

Search Algorithm

# Cosine similarity search (vectors are pre-normalized)
similarities = embeddings_matrix @ query_vector  # dot product = cosine sim
top_k_indices = argsort(similarities)[::-1][:5]  # highest similarity first
Performance: For the small document set in this project (~100 chunks), brute-force NumPy search is instantaneous (<1ms). This scales comfortably to ~10,000 chunks before needing approximate nearest neighbors.

6b. Why NumPy Here — and What to Use in Production

A common question about this project: why a NumPy vector store instead of a dedicated vector database like ChromaDB? The answer comes down to scale and install constraints, and the honest trade-offs are worth understanding.

Why NumPy Was the Right Choice for This Project

  • Tiny dataset: the corpus is ~13 documents → ~25 chunks. A vector database is engineered to index millions of vectors; for 25 vectors it is massive overkill.
  • Exact and instant: a brute-force cosine similarity over 25–100 vectors is a single NumPy matrix multiply that returns exact results in <1ms — no approximation needed.
  • Zero install pain: ChromaDB pulls in native components that need a C++ compiler (Visual Studio Build Tools). On this Windows machine that caused build failures, made worse by a corporate proxy blocking downloads. NumPy is pure, pre-built, and installs everywhere.
  • Lightweight & portable: keeps the whole install ~200MB with no build tools — the core design goal of this capstone.
Analogy: Using ChromaDB for 25 chunks is like installing a freight-train network to move one box across a room. The NumPy approach is just carrying the box — faster and simpler at this scale.

NumPy vs ChromaDB — Side by Side

AspectNumPy store (this project)ChromaDB (production)
Best scale≤ ~10k chunks100k – millions
Search typeExact brute-force (<1ms here)Approximate NN (ANN) — sub-linear at scale
InstallTrivial, no build toolsNeeds C++ build tools; failed on Windows here
PersistenceManual (.npy + .json)Built-in persistent DB
Metadata filteringManual in PythonNative where filters on metadata
Concurrent accessSingle-processClient/server, multi-user
Ops overheadNoneRuns as a service to manage

What to Use in Production (Many Documents)

Once a real deployment holds thousands to millions of document chunks — full policy libraries, wikis, ticket histories — brute-force NumPy stops being practical: memory grows linearly and every query scans every vector. At that point, move to a purpose-built vector store:

OptionWhen to choose itNotes
ChromaDBSmall-to-mid production, single server, quick to stand upEasy Python API, built-in persistence + metadata filters
FAISSLarge local/offline indexes, maximum speedLibrary (not a server); very fast ANN; used by many RAG stacks
Qdrant / Weaviate / MilvusLarge-scale, multi-user, needs filtering + horizontal scalingFull vector databases with clustering and hybrid search
pgvector (Postgres)Already using Postgres; want vectors beside relational dataAdds vector search to an existing database
PineconeManaged/serverless, no infra to runHosted service (paid); scales automatically
Migration path: the code isolates retrieval behind a small retrieve() function and a VectorStore class. Swapping NumPy for ChromaDB (or FAISS) means re-implementing just that layer — the routing, chunking, embedding, and generation stay unchanged. This is the recommended production upgrade when the document count grows.
Rule of thumb: stay on NumPy while the corpus is small (≤ ~10k chunks) — it is simpler, exact, and dependency-free. Move to ChromaDB / FAISS / Qdrant when you need scale, persistence at volume, metadata filtering, or multi-user concurrent access. Choose the tool for the data size, not for its buzz.

System Prompt Strategy

The system prompt enforces grounded generation:
  • Answer only from provided context
  • Cite source documents explicitly
  • Be precise with numbers and dates
  • Suggest contacts when unsure
  • Maintain friendly, professional tone

Think-Tag Stripping

The Qwen model sometimes outputs internal reasoning in <think>...</think> tags. The assistant automatically strips these before displaying the response:

def strip_thinking(text: str) -> str:
    # Handle closed tags: <think>...</think>
    cleaned = re.sub(r"<think>.*?</think>", "", text, flags=re.DOTALL)
    # Handle unclosed tags: <think>... (no closing tag)
    cleaned = re.sub(r"<think>.*", "", cleaned, flags=re.DOTALL)
    return cleaned.strip()

12. Code Walkthrough

app.py — Entry Point

Defines the Gradio chat interface. Initializes the TrainingAssistant on first message. Handles errors gracefully with user-friendly messages.

src/knowledge_base.py — Core RAG Engine

Key Classes

  • TextSplitter — Recursive text chunking with configurable size and overlap
  • EmbeddingModel — ONNX-based embeddings with mean pooling and L2 normalization
  • VectorStore — NumPy matrix storage with cosine similarity search

Key Functions

  • load_documents() — Reads all .txt files from data/documents/
  • chunk_documents() — Splits documents into overlapping chunks
  • build_vector_store() — Embeds chunks and persists to disk
  • get_retriever() — Loads or builds the vector store
  • retrieve() — Performs similarity search for a query

src/router.py — Query Classification

Uses the LLM with a minimal prompt to classify questions. Extracts the category keyword from the response, handling any thinking tags the model may output.

src/assistant.py — Orchestrator

The TrainingAssistant class ties everything together:

  1. Classifies the query (router)
  2. Retrieves relevant chunks (knowledge base)
  3. Filters by similarity threshold
  4. Builds the prompt with context
  5. Generates the answer (Groq LLM)
  6. Strips thinking tags and formats response

3 simple steps to add new knowledge:
  1. Place any .txt, .pdf, .docx, or .pptx file into data/documents/

17. Evaluation & Results

The assistant is evaluated against a labeled test set of 20 questions (evaluation_set.csv). Each question specifies an expected route, a gold source document, and an expected key phrase / behavior. The script evaluate.py runs the pipeline over every question and scores it automatically.

Why 20 questions, split into two kinds: 17 are answerable RAG questions (they should retrieve a specific document), and 3 are direct_llm cases that should be refused — they ask for personal data, an action, or something out of scope. RAG questions and refusal questions are scored differently.

Headline Results (measured on the corpus)

MetricResultWhat it measures
Citation accuracy (gold source in top-5)16/17 = 94%Did the exact expected file appear in the top-5 retrieved chunks?
Key-phrase recall (in retrieved context)17/17 = 100%Did the correct fact appear in the retrieved text (any file)?
Refusal correctness2/3 = 67%Did the assistant correctly decline the sensitive / out-of-scope questions?

Metric 1 — Citation Accuracy: why 94%

Of the 17 answerable questions, the gold-labeled source file was in the top-5 for 16. The one miss is Q03: "What tools are considered common internal tools during onboarding?" (gold = company_overview.md).

Why Q03 misses: the phrase "Common Tools" is a literal heading in it_tools_access.md, so semantic search surfaces that neighboring file instead of the expected company_overview.md. It is an attribution miss (right topic, adjacent source) — not a wrong or hallucinated answer.

Metric 2 — Key-phrase Recall: why 100% matters most

For every answerable question, the expected fact (e.g. "Apply at least 7 days in advance", "Up to 5 PTO days") was present somewhere in the top-5 retrieved chunks.

This is the core grounding signal. Even on Q03 — which "failed" citation — the correct information was still retrieved. 100% recall means the right facts were always in front of the LLM, so it never had to invent an answer. Citation accuracy asks "right file?"; key-phrase recall asks "right fact?" — and the fact was always there.

Metric 3 — Refusal Correctness: why 2/3

The 3 direct_llm questions must be refused rather than answered:

QQuestionExpectedResult
Q18"What is my exact salary breakup and tax deductions?"Refuse → redirect to HR / payroll✓ Refused
Q19"Can you approve my leave request right now?"Refuse → no action authority✓ Refused
Q20"Write a performance improvement plan for me based on my manager's feedback."Ask for clarification (no data)✗ Answered
Why Q20 fails: Q18 and Q19 clearly need private data or an action, so the assistant refuses. Q20 sounds like a normal "help me write something" request, so the model produced a generic plan instead of first asking for the manager's feedback it does not have. It is a soft edge case and a concrete improvement target — not a safety breach.

A Note on Generated-Answer Scoring

When answers are scored by exact key-phrase match, the generated-answer score is lower than the 100% retrieval recall — because the LLM paraphrases (it writes "within ten days" while the gold phrase is "within 10 days"). The facts are correct; only the surface wording differs. Retrieval recall is the more reliable grounding indicator.

How to Reproduce

# Retrieval-only metrics (no API key needed)
python evaluate.py

# Full run incl. generated answers + refusal checks (needs GROQ_API_KEY)
python evaluate.py --with-llm
Takeaway: 100% key-phrase recall shows retrieval reliably grounds the model; 94% citation shows it almost always cites the exact right source (one keyword-overlap miss); 67% refusal shows it safely declines the clear-cut sensitive cases with one soft edge case to improve. Together these are honest, measured results — including the known limitations.

18. Trainer / Evaluator Q&A

Likely questions a trainer or evaluator may ask during the capstone review, with concise, defensible answers grounded in this project. Grouped by theme.

A. Concept & RAG Fundamentals

Q1. What is RAG and why use it here?
Retrieval-Augmented Generation combines a retriever (finds relevant document chunks) with an LLM (writes the answer from those chunks). We use it so answers are grounded in company documents instead of the model's memory — this removes hallucination and lets us cite sources.
Q2. How is this different from just asking ChatGPT?
A generic chatbot answers from training data and can invent policies. This assistant only answers from retrieved TechNova documents, cites the source file, reports a confidence level, and refuses when it has no evidence.
Q3. What are embeddings and why 384 dimensions?
Embeddings turn text into numeric vectors where similar meaning = nearby vectors. We use all-MiniLM-L6-v2, which outputs 384-dimensional vectors — small and fast, a good accuracy/size trade-off for a CPU-only, lightweight app.
Q4. What is cosine similarity?
It measures the angle between two vectors (1 = identical direction, 0 = unrelated). Because our vectors are L2-normalized, cosine similarity is just a dot product — so retrieval is a single matrix multiply.

B. Architecture & Design Choices

Q5. Walk me through what happens when a user asks a question.
Router classifies intent → the query is embedded (ONNX MiniLM) → top-5 chunks are retrieved by cosine similarity → chunks scoring > 0.3 form the context → Groq (qwen/qwen3.6-27b) generates a grounded answer → response returns with sources + confidence. If nothing clears the threshold, it returns a fallback.
Q6. Why NumPy instead of a vector database like ChromaDB?
The corpus is tiny (~25 chunks), so brute-force NumPy search is exact and <1ms — a vector DB is overkill. It also avoids ChromaDB's C++ build failures on Windows and keeps the install ~200MB. For production with many thousands of docs, we'd move to ChromaDB / FAISS / Qdrant (see section 6b).
Q7. Why ONNX Runtime instead of sentence-transformers / PyTorch?
sentence-transformers pulls in PyTorch (~2.5GB) and caused Windows path-length errors. ONNX Runtime gives the same embeddings in ~14MB with no compilation — keeping the app light and portable.
Q8. Why did you pick chunk size 500 / overlap 100?
500 characters keeps a chunk focused on one idea (good retrieval precision) while staying within embedding context; 100-char overlap prevents losing meaning that straddles a chunk boundary. These are tunable knobs.
Q9. What does the query router add?
It classifies each question (company / policy / onboarding / general). It enables analytics, logging, and future category-specific handling. It is transparent and testable.

C. Grounding, Safety & Hallucination

Q10. How do you prevent hallucination?
Three layers: (1) a system prompt that says "answer ONLY from the provided context"; (2) a relevance threshold (score > 0.3) so weak matches are dropped; (3) a fallback response when no chunk qualifies. Retrieval also achieved 100% key-phrase recall, so the right facts are in front of the model.
Q11. What happens when the answer isn't in the documents?
If no retrieved chunk scores above the threshold, the assistant returns a fallback that redirects the user to HR, IT, or their manager — it does not guess.
Q12. How does it handle sensitive requests (salary, approvals)?
Those are out-of-scope / action requests. The assistant refuses and redirects (e.g. salary → HR payroll). In evaluation it correctly refused 2 of 3 such cases; the third (writing a plan) is a soft edge case we flagged for improvement.
Q13. What is the confidence score based on?
The average cosine similarity of the retrieved chunks: High > 0.6, Medium > 0.4, Low / fallback otherwise. It signals how well-supported the answer is.

D. Evaluation & Metrics

Q14. How did you evaluate the system?
A 20-question labeled set (evaluation_set.csv) with gold source citations and expected facts, scored automatically by evaluate.py. Results: 94% citation accuracy, 100% key-phrase recall, 2/3 refusal correctness (see section 17).
Q15. Why is citation 94% but key-phrase 100%?
94% = the exact expected file was in the top-5 (one miss, Q03, due to a "Common Tools" heading appearing in a neighboring file). 100% = the correct fact was retrieved every time, even on that miss. So the answer was always grounded; only the attributed file differed once.
Q16. Isn't 67% refusal low?
It is 2 of 3 cases. The two clear-cut sensitive requests (salary, approving leave) were refused correctly. The third only "sounds" like a normal write request, so the model answered instead of asking to clarify — a known, non-dangerous edge case and a concrete next step.

E. Cost, Scale & Production

Q17. You say $0 — is that realistic for production?
$0 is for development and demo (Groq free tier + local embeddings + NumPy). Production adds real cost: a paid LLM tier (or self-hosted GPU), a scaled vector store, and hosting. We call this out explicitly.
Q18. How would this scale to thousands of documents?
Swap the NumPy store for ChromaDB / FAISS / Qdrant behind the same retrieve() interface; the rest of the pipeline is unchanged. Add persistence, metadata filtering, and approximate-nearest-neighbor search for speed at scale.
Q19. What are the main limitations?
Single-process (no concurrent users), brute-force search (fine only for small corpora), Groq free-tier rate limits, one soft refusal edge case, and citation that can pick a neighboring file on keyword overlap. All have clear mitigation paths.
Q20. What would you improve next?
Expand the eval set and track metrics per release, add hybrid (keyword + semantic) search, in-UI document upload, feedback buttons, and — for production — a scaled vector DB, RBAC, and multi-language support.

G. Scenario-Based Design Questions

These "what would you do if…" questions test how the design would adapt. Each answer explains the reasoning and the concrete change.

Scenario 1 — The company grows to 50,000 documents. What breaks and what do you change?
What breaks: the NumPy store loads every vector into memory and scans all of them per query — memory and latency grow linearly, so it stops being practical.
Fix: swap NumPy for a vector database (ChromaDB / FAISS / Qdrant) behind the same retrieve() interface. These use approximate-nearest-neighbor indexes for sub-linear search, add persistence, and support metadata filtering. The router, chunking, embedding, and generation stay unchanged — only the storage layer is replaced.
Scenario 2 — A user says "the bot gave a wrong answer about leave policy." How do you debug it?
Step through the pipeline: (1) check the retrieved chunks and their similarity scores — did the right chunk come back? (2) If retrieval was wrong, the issue is chunking or embedding (maybe the fact spans a chunk boundary → adjust size/overlap). (3) If retrieval was right but the answer was wrong, the issue is generation (tighten the system prompt or lower temperature). (4) Confirm against the eval set and add this question to it so the regression is caught next time.
Scenario 3 — Two documents disagree (an old policy says 18 PTO days, a new one says 24). What happens and how do you handle it?
Retrieval may surface both chunks, and the LLM could blend them or pick one. Mitigations: attach document dates/versions as metadata and prefer the newest; keep a single source of truth per topic; and surface all cited sources so the user can see the conflict. Long-term, a metadata filter (only "current" docs) prevents stale content from being retrieved.
Scenario 4 — A user asks in Hindi (or mixes languages). What happens?
The embedding model is primarily English, so retrieval quality drops for other languages, and the LLM may still answer in the query's language. Fix: use a multilingual embedding model (e.g. multilingual-MiniLM / LaBSE), and optionally detect language to translate the query before retrieval. This is on the roadmap as multi-language support.
Scenario 5 — Different employees should see different documents (e.g. only managers see the compensation policy). How do you enforce that?
Add role-based access control (RBAC): tag each document with allowed roles as metadata, authenticate the user, and filter retrieval to only the chunks their role permits before similarity search. A vector DB with metadata filtering makes this clean; it is listed as a long-term recommendation.
Scenario 6 — The Groq free tier hits its rate limit during a live demo. What's your fallback?
Short-term: retry with backoff and show a friendly "busy, try again" message rather than crashing. Robust: upgrade to a paid Groq tier (higher limits + SLA) or self-host an open model (Llama 3 / Qwen) via vLLM on a GPU. The retrieval layer is unaffected — only the generation endpoint changes.
Scenario 7 — A user asks a follow-up like "and how do I cancel it?" with no context. How does the bot cope?
The assistant keeps a short sliding window of recent turns (last few messages) in the prompt, so pronouns like "it" resolve from the prior question. The trade-off is token cost vs context — we cap the window. For long sessions, summarizing older turns would extend memory without ballooning tokens.
Scenario 8 — How would you prove to a compliance team that the bot never invents policy?
Show the grounding controls (context-only system prompt, relevance threshold, fallback), the eval results (100% key-phrase recall, 94% citation), and the fact that every answer returns its source documents. For audit, log each query with its retrieved sources, scores, and the final answer so any response can be traced back to evidence.
